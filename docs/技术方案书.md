## 一、研究背景与问题定义

### 1.1 研究背景

微短剧是 2023 年以来增长最快的内容形态之一：单集 1–3 分钟、总集数常达 80–150 集、
以"强钩子 + 高频反转"驱动用户连续追更。随着 AI 生成技术进入剧本、配音、画面环节，
"AI 短剧"进一步把单部剧的制作周期压缩到数周，**同一赛道内供给量迅速膨胀**。

在这种供给过剩的环境下，制作方与平台运营方共同关心一个业务问题：

> **一部微短剧上线后，能否进入热度头部？决定它能不能"爆"的关键因素是什么？**

与"发布后几小时的播放量预测"不同，微短剧的热度在**上线后数周内持续累积**，
且其热度由平台榜单给出统一口径，适合做横截面的影响因素分析。

### 1.2 问题定义

将业务问题形式化为两个学习任务，其中分类为主任务、回归为副任务：

**任务 A（主）· 爆款识别 — 二分类**

$$
y_i = \mathbb{1}\left[\text{heat}_i \ge Q_{0.80}(\text{heat})\right]
$$

即：该剧热度是否进入全量 Top 20%。正类占比 20.00%，阈值 **4,815 万**。

**任务 B（副）· 热度回归**

$$
y_i = \log_{10}(\text{heat}_i)
$$

采用对数尺度是因为热度长尾；同时便于用"平均绝对误差（万）"给出业务可读的解释。

### 1.3 与既有研究的差异

现有短视频热度预测研究多以 TikTok / YouTube 为对象，特征集中在**视频级互动时序**
（前 1 小时点赞、播放增长曲线）与**创作者体量**（粉丝数、历史作品均值）。
本研究的不同在于：

1. **对象是剧集级而非视频级**——微短剧以"部"为消费单位，热度在剧集粒度上沉淀；
2. **引入剧集文本与题材语义**——简介剧情梗概被归纳为 10 类"爽点"标签；
3. **显式区分"上线前可得"与"上线后观测"两类特征**，并用量化消融回答
   "观众反馈到底能带来多少增量信息"。

| 表3 | `表3_AI剧第一集评论列表.xlsx` | 11,977 | **11,168** | 7 | 每部剧第一集评论 |

### 2.2 数据质量与清洗

清洗策略与损失明细：

| 处理 | 表2 | 表3 | 说明 |
|---|---|---|---|
| 完全重复行 | 0 | 0 | — |
| 同人同文重复 | 0 | 6 | 同一用户在剧内重复发言 |
| 空评论（清洗后为空） | 38 | 803 | 仅含表情占位符或无内容 |
| 时间解析失败 | 0 | 0 | — |
| **保留** | **6,769** | **11,168** | — |

**外键完整性**：表2 覆盖 793/800 部（99.1%），表3 覆盖 800/800 部（100%），
无孤儿记录。7 部剧无热评明细，建模时以榜单均分兜底。

**一致性校验**：`heat_text` 解析值（如"6849万热度"→ 68,491,671）与 `heat_value`
的**一致率 100%**（容差 1%）。

### 2.3 异常值治理

采用**对数域 3σ 检测 + 标记**策略，关键决策是**对标签不做截尾**：

| 字段 | 处理 | 区间 | 标记数 | 理由 |
|---|---|---|---|---|
| `episodes` | 3.5σ 截尾 | [19, 500] | 9 | 个别"合集"上传达 1000 集，非真实剧集节奏 |
| `heat_value` | **仅标记，不截尾** | 不修改 | 30 | 热度是**被预测对象**；截尾会把 Top 剧集压平成同一值，破坏回归目标并误导结论 |

## 三、数据管理设计（模块一）

### 3.1 分层数据仓库模型

```
ODS 原始层   drama_info / drama_hot_comment / drama_ep1_comment
                  ↓ 聚合
DWS 汇总层   drama_comment_agg            评论侧剧集级指标
                  ↓ 特征化
ADS 应用层   drama_feature_wide           建模特征宽表（一类样本一行）
                  ↓
VW  视图层   v_heat_rank / v_genre_heat / v_comment_signal
```

建表脚本见 `sql/douyin_schema.sql`，采用 utf8mb4 字符集（剧名与评论含 emoji），
并建立外键约束保证 ODS 层引用完整性。

### 3.2 视图设计

- `v_heat_rank`：热度排行榜，附题材与互动概况；
- `v_genre_heat`：题材热度画像。利用 `SUBSTRING_INDEX` + 数字辅助表把多标签
  `category` **炸开为单标签行**，统计各题材的剧数、平均/最高热度与爆款率；
  题材阈值取 `drama_cnt ≥ 19`，正好落在建模所用的 **20 种题材**上，
  使"SQL 视图口径"与"特征工程口径"严格一致；
- `v_comment_signal`：口碑 / 互动 / 态度三类信号并排展示，供人工核查。

> 三个视图在 SQLite 降级通道中同样可用。差异只在 `v_genre_heat`：
> SQLite 无 `SUBSTRING_INDEX`，多标签炸开改在 Python 侧物化为辅助表 `genre_split`
> 后再建视图，**结果集与 MySQL 版完全一致**（均为 20 行）。

### 3.3 数据治理巡检

`load_mysql.py --check` 实现六维巡检，输出结论供答辩演示：

| 维度 | 检查内容 | 本次结果 |
|---|---|---|
| 唯一性 | 三表主键重复数 | 0 / 0 / 0 |
| 完整性 | 评论表对剧集的覆盖率、外键孤儿 | 99.1% / 100%，孤儿 0 |
| 一致性 | 热度文本 ↔ 数值一致率 | 100% |
| 有效性 | 集数、热度、评分、点赞的数值域 | 越界 0 |
| 隐私性 | 标识类字段识别与处理声明 | `user_id` 在 ODS 入库层与建模层双重剔除 |

> **无 MySQL 环境时的降级**：`load_mysql.py --export`（或 `build_sql.py`）会把
> ODS 三表 + DWS + ADS 共 **5 张业务表、1 张多标签辅助表（`genre_split`）与 3 个视图**
> 写入 `outputs/douyin_drama.sqlite`，保证在任意机器上都能演示"多表存储 + 视图查询"。
> 降级通道的列定义与 `sql/douyin_schema.sql` 严格对齐（`rank` → `rank_no`，
> 并剔除标识类字段 `user_id`），因此同一套视图 SQL 在两侧都跑得通。

## 四、大数据预处理与特征工程（模块二）

### 4.1 特征体系（64 维）

特征按**可得时点**分为四组，这是后续消融实验的基础：

#### 组一 · 内容属性（40 维，上线前可得）

| 子类 | 维度 | 特征 |
|---|---|---|
| 体量 | 3 | `episodes`、`log_episodes`、`is_long_series`(≥100集) |
| 题材 | 21 | `n_genre_tags` + 20 个 `tag_*`（逆袭/都市/剧情/乡村/年代/重生/豪门/穿越/脑洞/古代/种田/恋爱/异能/系统/萌宝/总裁/架空/玄幻/宫廷/职场） |
| 剧名 | 3 | `title_len`、`title_has_season`、`title_has_number` |
| 简介 | 3 | `summary_len`、`summary_has_question`、`summary_has_exclaim` |
| 剧情爽点 | 10 | `plot_*`：重生穿越 / 复仇逆袭 / 金手指 / 豪门世家 / 家庭亲情 / 年代乡村 / 权谋宫廷 / 萌宝治愈 / 战神武力 / 情感虐恋 |

**题材标签筛选**：`category` 原始拆分出 **48 种**标签，仅保留出现频次 ≥ 19 的
**20 种**作为特征，长尾归入"其他"——避免稀疏列稀释树模型的分裂增益。

**爽点提取**：对每类爽点定义关键词词典（`config.PLOT_KEYWORDS`），统计简介中的命中次数。
例如"重生穿越"匹配 `重生/穿越/转世/回到/醒来/魂穿/投胎`。

#### 组二 · 观众口碑（5 维，上线后）

`hot_rating_avg`（榜单均分）、`hot_rating_mean`、`hot_rating_std`（评分分歧度）、
`hot_rating_good`（好评率 ≥9 分）、`hot_rating_bad`（差评率 ≤3 分）。

#### 组三 · 评论互动（13 维，上线后）

| 子类 | 特征 |
|---|---|
| 热评侧 | `hot_cmt_cnt`、`hot_digg_mean`、`log_hot_digg_max`、`log_hot_digg_sum`、`hot_hot_ratio`(百赞占比)、`hot_user_div`(用户多样性) |
| 第一集评论侧 | `ep1_cmt_cnt`、`ep1_digg_mean`、`log_ep1_digg_max`、`log_ep1_digg_sum`、`ep1_hot_ratio`、`ep1_super_ratio`(千赞占比)、`ep1_user_div` |

长尾计数一律做 `log1p` 变换。

#### 组四 · 文本态度（6 维，上线后）

`hot_text_len`、`ep1_text_len`、`ep1_emoji_ratio`、`ep1_urge_ratio`（催更率）、
`ep1_pos_ratio`、`ep1_neg_ratio`——后三者基于 `config` 中的情感词典做关键词命中率统计。

### 4.2 防数据泄漏设计

这是本工程最需要交代清楚的一点：

| 排除项 | 排除理由 |
|---|---|
| `heat_value` / `heat_text` / `rank` / `rank_tag` | 标签本身或其单调变换（rank 与 heat 的 Spearman = **−0.956**） |
| `like_count` / `collect_count` | 与热度同源，属于平台热度公式的构成项 |
| `comment_time` 及其派生量 | 会造成"越近期上线的剧评论越新 → 热度越高"的伪相关 |

### 4.3 标签构造

```python
heat_value  →  is_hot  = (heat_value >= heat.quantile(0.80))   # 主任务
            →  log_heat = log10(heat_value)                     # 副任务
            →  heat_tier = qcut(rank, 4)                        # 分档（EDA 用）
```

阈值 = **48,157,000**，正类占比 **20.00%**。

## 五、大数据分析（模块三）

### 5.1 热度形态：高度集中的榜单分布

| 分位 | P25 | P50 | P75 | P90 | Max |
|---|---|---|---|---|---|
| 热度（万） | 4,609 | **4,661** | 4,776 | 4,970 | 6,849 |

热度最小值 4,430 万、最大值 6,849 万，**变异系数仅 5.97%**。
这直接决定了本研究的方法论基调：**不是"预测精确点位"，而是"识别头部与其余的系统性差异"**。

### 5.2 榜单结构

按排名分档统计热度中位：前 50 名 5,516 万 → 尾部（701–800 名）4,601 万，
**头部与尾部相差约 915 万（约 20%）**，而腰部区间（201–600 名）几乎持平。
99 部剧带"热播AI剧榜第 N 名"标签，与热度高度对应。

### 5.3 单变量关联强度（Spearman 秩相关）

| 排名 | 特征 | 分组 | 秩相关 |
|---|---|---|---|
| 1 | 热评点赞合计(对数) | 评论互动 | **0.239** |
| 2 | 热评平均点赞 | 评论互动 | 0.235 |
| 3 | 最高热评点赞(对数) | 评论互动 | 0.215 |
| 4 | 热评平均字数 | 文本态度 | 0.164 |
| 5 | 总集数 | 内容属性 | 0.159 |
| … | … | … | … |
| 末位 | 热评均分（口碑） | 观众口碑 | **0.017** |

**结论**：评论互动量是最强的单变量信号；口碑评分几乎不携带热度信息。

### 5.4 分层对照：互动强度 → 爆款率

按第一集评论平均点赞分 8 档（等样本量）：

| 档位 | D1 | D8 |
|---|---|---|
| 爆款率 | **16.0%** | **31.0%** |

单调递增，说明评论互动与爆款概率之间存在稳定关系。

### 5.5 题材画像

爆款率 Top5 题材：**萌宝 50%**、**宫廷 47%**、总裁 29%、古代 27%、异能 26%，
均显著高于全站基线 20%；而样本量最大的"逆袭"（408 部）爆款率仅 17%——
高供给赛道的竞争更激烈。

### 5.6 时间规律

评论集中在 **2026-09**（占 9 月 + 10 月合计约 90%），峰值时段 **20 时**，
晚间（18–23 时）占全部评论的 **33.2%**。

## 六、大数据挖掘（模块四）

### 6.1 实验设计

| 实验 | 目的 | 设计 |
|---|---|---|
| 一 · 多模型对比 | 验证 XGBoost 的优势 | LR / DT / RF / GBDT / XGBoost，5 折 CV + 20% 测试集 |
| 二 · 热度回归 | 副任务建模 | 岭回归 / RF / XGBoost |
| 三 · 特征组消融 | 量化观众反馈的增量贡献 | 4 组特征逐层累加，4×5 折重复交叉验证 |
| 四 · 稳健性 | 小样本下的结果稳定性 | 10 次不同随机划分 |
| 五 · 可解释性 | 影响因素归因 | XGBoost 增益重要性 + SHAP |

**阈值策略**：不使用固定 0.5，而是先在**袋外（OOF）预测**上搜索使 F1 最大的阈值，
再应用于测试集——避免"用测试集调参"这一常见方法论瑕疵。

### 6.2 实验一结果：爆款二分类

| 模型 | AUC | F1 | AP | 准确率 | 阈值 |
|---|---|---|---|---|---|
| **XGBoost** | **0.6946** | **0.4407** | **0.4867** | 0.7938 | 0.250 |
| 梯度提升树 GBDT | 0.6853 | 0.3765 | 0.4647 | 0.6688 | 0.170 |
| 随机森林 | 0.6841 | 0.4062 | 0.4339 | 0.7625 | 0.275 |
| 逻辑回归（基线） | 0.6316 | 0.3377 | 0.3684 | 0.6812 | 0.235 |
| 决策树 | 0.6281 | 0.3894 | 0.2952 | 0.5688 | 0.160 |

> 完整指标见 `outputs/model_comparison.csv`（`RANDOM_SEED=42` 固定，可精确复现）。

**XGBoost 相对线性基线的 AUC 提升为 +0.063**，说明影响因素之间存在**非线性与交互效应**，
单纯线性模型无法充分刻画。

### 6.3 实验二结果：热度回归

| 模型 | R² | MAE(log) | 平均绝对误差 |
|---|---|---|---|
| **XGBoost** | **0.2035** | 0.0148 | 171 万 |
| 随机森林 | 0.1690 | 0.0153 | 176 万 |
| 岭回归（基线） | 0.0925 | 0.0165 | 189 万 |

R² 偏低的**解释**：热度变量本身变异系数仅 6%，信噪比极低；模型从 189 万的
误差降到 171 万已属有效改进，但绝对精度受限于数据本身的可分辨度。

### 6.4 实验三结果：特征组增量消融

| 特征组 | 维度 | AUC | AP | 增量 |
|---|---|---|---|---|
| 仅内容属性 | 40 | 0.6328 | 0.3764 | — |
| + 观众口碑 | 45 | 0.6495 | 0.3903 | +0.0167 |
| + 评论互动 | 58 | 0.7022 | 0.4597 | **+0.0526** |
| 全特征（+ 文本态度） | 64 | **0.7189** | 0.4702 | +0.0167 |

**这是本研究的核心实验**：观众反馈特征合计带来 **+0.0861** 的 AUC 增量，
其中**评论互动单项贡献最大（+0.0526）**。也就是说：

- 仅凭"选题 + 集数 + 简介"这些上线前信息，判别能力有限（AUC 0.633）；
- 一旦观测到观众反馈，判别能力显著跃升（AUC 0.719）。

业务含义：**微短剧的爆款潜力在"上线前"只能被部分预测，上线初期的观众反馈才是关键的修正信号。**

### 6.5 实验四结果：稳健性

10 次随机划分下：AUC **0.6860 ± 0.0528**（区间 0.5825 ~ 0.7507），F1 0.4119 ± 0.0439。
在 800 样本、64 特征、20% 正类率的小样本设定下，该波动幅度处于合理区间，
说明结论具备可复现性。

## 七、数据可视化（模块五）

### 7.1 产出形态

`webapp/`：**分层解耦的 Flask Web 应用**，启动后监听 `0.0.0.0:5000`，
提供四个页面：工作台总览 / 新剧实时预测 / 模型评估与归因 / 数据集浏览。

依赖方向单向向内，与训练流水线完全隔离——领域层不知道 Flask 存在，
仓储层是唯一接触文件系统的地方：

```
视图层 (templates / static)
   ↓ HTTP
接口层 (app/api · views)          路由、参数、状态码
   ↓
服务层 (app/services)             业务编排：feature / model / insight / dataset
   ↓            ↓
领域层 (app/domain)          仓储层 (app/repositories)
纯算法，零框架依赖            唯一接触文件系统
```

> **为何不用单文件 HTML**：单文件形态把数据、算法与界面耦合在一个文档里，
> 既无法分层讲解系统设计，也无法承接"新剧实时预测"这类需要服务端持续演进的
> 需求（如后续接入爬虫）。改为应用工厂 + 蓝图 + 依赖装配容器的分层结构后，
> 替换数据源、更换特征构造或调整决策规则都只影响单层。

### 7.2 部署推理引擎的实现

服务端不加载任何 `.pkl` 模型对象，而是直接消费导出脚本产出的树结构 JSON。
这不是简单的格式转换，而是一次**定点数值移植**，有三个必须处理的工程细节：

**（1）树结构扁平化**
用 `booster.trees_to_dataframe()` 抽取全部节点，编码为四个定型数组：
`i` = int16×3（特征下标 / 左子 / 右子）、`d` = int8（缺失默认方向）、
`t` = float64（分裂阈值）、`v` = float64（叶子值，位于 log-odds 空间），
base64 编码后写入 `outputs/dashboard/webmodel.json`。
服务启动时一次性解码常驻内存，此后每次预测只做数组寻址。

**（2）base_score 截距标定**
不同 XGBoost 版本对 `base_score` 的变换口径不一致（概率域 vs margin 域）。
本工程不依赖文档，而是**实测标定**：

$$
b = \text{median}\big(\text{margin}(x) - \sum_{\text{trees}} \text{leafvalue}(x)\big)
$$

若走树逻辑与 XGBoost 一致，该值必为常数（实测为 −1.386295 = logit(0.20)）。

**（3）float32 比较精度对齐** ← 最容易踩的坑
XGBoost 内部把特征值与分裂阈值都降到 **float32** 再比较。
若推理端用 float64 比较，恰好贴着阈值的样本会走错分支：

| 比较方式 | offset 标准差 | 概率最大偏差 |
|---|---|---|
| `float64(x) < float64(t)` | 1.5e-02 | **1.8e-02** |
| `float32(x) < float32(t)` | 7.8e-07 | **2.1e-07** |

因此推理端对**两侧**都施加 float32 截断（`np.float32`）。导出脚本内置自检：
解码后重算样本概率与 Python 侧逐条比对，**偏差 ≥ 1e-6 即中断构建**，
从根本上杜绝"服务静默给错数"。

**（4）与训练端的一致性验证**
`webapp/app/domain/forest.py` 的走树结果与导出侧参考实现逐样本比对，
**最大偏差 1e-16**（仅浮点舍入），据此可判定两套实现语义等价。

### 7.3 双模型对比设计

服务并列部署两个模型，把消融实验的结论**产品化**：

| 模型 | 特征 | 树/节点 | 测试 AUC |
|---|---|---|---|
| 冷启动版 | 内容属性 40 维 | 300 棵 / 5,030 节点 | 0.6677 |
| 全特征版 | 内容 + 观众反馈 50 维 | 120 棵 / 1,472 节点 | 0.6843 |

使用者调整参数时，两个概率同时刷新，并显示"追加观众反馈后提升 +N 个百分点"，
让"观众反馈带来增量"这一学术结论变成可直接感知的交互。

### 7.4 图表取舍与题材选题决策

按"图表为预测结论服务"的原则，图表按**页面职责**分布，不做无差别堆砌：

| 页面 | 图表 / 面板 |
|---|---|
| 工作台总览 `/` | ROC 双模型判别能力 · 全局影响因素重要性（Top 12，按四类特征组着色） |
| 新剧实时预测 `/predict` | 题材选题决策面板（含 Wilson 区间，见下） |
| 模型评估与归因 `/model` | 模型对比 · 回归对比 · 消融实验 · 稳健性 · SHAP Top 特征 |
| 数据集浏览 `/dataset` | 题材爆款率画像 · 核心指标分布 |

#### 7.4.1 为什么把"选题"单独做成面板

前四组实验回答的是"什么在影响热度"，但业务方真正要下的是**选题决策**。
因此把全部 20 个题材的爆款率、**95% Wilson 置信区间**与样本量放在同一张图里，
并按四档给出可直接执行的建议：

| 档位 | 判据 | 当前结果 |
|---|---|---|
| **首选** | 置信区间下界 > 全站基准（20%）——统计上显著 | 萌宝 50%（n=34）、宫廷 47%（n=19） |
| **优先** | 点估计 ≥ 基准 × 1.2 | 总裁 29% · 古代 27% · 异能 26% · 脑洞 24% |
| **中性** | 基准 × 0.8 ~ × 1.2 | 豪门 / 重生 / 都市 / 乡村 / 穿越 / 系统 / 玄幻 / 年代 / 逆袭 / 种田 / 恋爱 |
| **规避** | 点估计 < 基准 × 0.8 | 职场 16% · 架空 14% · 剧情 14% |

**为何必须同时给出置信区间**：宫廷只有 19 部，"47%"这个点估计的区间宽达
27%~68%；而剧情有 325 部，13.8% 的区间仅 10.5%~18.0%——
**它是唯一统计上显著低于基准的题材**。若不展示区间宽度，
读者会把"19 部里 9 部爆了"与"325 部里 45 部爆了"当成同等强度的证据。
区间采用 **Wilson 得分区间**而非正态近似：题材样本小且比例靠近 0/1 时，
正态近似会给出越界区间（甚至负值）。

#### 7.4.2 双标签组合榜

`category` 本身是多标签字段，组合常强于单标签，故同屏给出
"样本 ≥15 的双标签组合"中最优与最差各若干条：

- **最优**：古代+宫廷 46.7% · 脑洞+古代 41.7% · 乡村+古代 40.7% · 重生+脑洞 36.4%
- **避雷**：年代+恋爱 5.9% · 种田+系统 6.2% · 剧情+职场 6.7% · 穿越+异能 8.3%

最优与最差相差 **40.8 个百分点**，说明"题材组合"这一前置信号的跨度远大于单标签。

### 7.5 界面视觉设计

采用**浅色工具风**——单一品牌色 + 中性灰阶，不使用霓虹光晕与玻璃拟态：

- **三层样式表分职**：`tokens.css` 集中定义全部设计变量（色彩 / 间距 / 字号 / 字体栈），
  `base.css` 负责版式与语义标签，`components.css` 负责卡片、表格、标签等组件；
  其余样式一律通过 `var()` 引用，不出现裸色值与裸间距，换肤只改一处；
- 卡面为纯白 + 1px 细边框 + 极轻投影，不使用半透明玻璃与多层渐变；
- 数值统一等宽字体；正负贡献与档位用**红涨绿跌**语义色区分，符合国内数据看板惯例；
- 图表配色在 `static/js/charts.js` 中集中定义，与 CSS 变量同源，
  避免"改主题要逐个改图表"的割裂（此前深色版图表色为 JS 硬编码，是明确的返工点）；
- 解释性文案压缩到最低，页面只保留必要说明与判据注释，可复核但不说教。

> **取舍说明**：答辩投影场景下浅色高对比更稳定；克制装饰（无发光、无多层渐变、
> 无逐段入场动效）也更接近常规业务系统的观感。原先的深色霓虹风正是"AI 味"的
> 主要来源，故整体替换而非局部调整。

## 八、结论

1. **XGBoost 显著优于线性基线**（分类 AUC 0.6946 vs 0.6316；回归 R² 0.2035 vs 0.0925），
   证明微短剧热度的影响因素之间存在非线性与交互效应。
2. **观众反馈是关键增量信息**：内容属性单独 AUC 0.6328，加入观众反馈后升至 0.7189
   （**+0.0861**），其中评论互动的边际贡献最大（+0.0526）。
3. **评论互动 > 口碑**：热评点赞合计的秩相关 0.239，而热评均分仅 0.017。
   "叫好"与"叫座"在这个赛道上是两件事。
4. **题材携带显著先验**：萌宝（50%）、宫廷（47%）的爆款率远高于全站 20%，
   且是仅有的两个**置信区间下界仍高于基准**的题材；供给最密集的"逆袭"（408 部）
   爆款率仅 17.4%；剧情是唯一**统计上显著偏低**的题材（13.8%，n=325）。
   双标签组合的跨度更大：古代+宫廷 46.7% 对 年代+恋爱 5.9%，相差 40.8 个百分点。
5. **负向因子同样有信息量**：评论字数长、催更占比高对应更低热度，
   可作为"内容节奏可能有问题"的预警信号。

## 九、局限与展望

| 局限 | 说明 | 改进方向 |
|---|---|---|
| 横截面而非严格时序 | 评论与热度在同一快照期内观测，"预测"更接近"归因" | 接入多时点快照（上线 24h/72h/7d），构造真正的提前预测任务 |
| 热度区分度低 | 变异系数仅 6%，限制了回归可达到的 R² 上限 | 争取拿到播放量/完播率等原始指标 |
| 样本量偏小 | 800 部，10 次划分 AUC 标准差 0.053 | 扩大榜单抓取范围至多个垂类榜 |
| 文本特征较浅 | 采用关键词词典而非语义模型 | 引入中文预训练模型做评论情感与主题挖掘 |
| 榜单选择偏差 | 样本本身是"已上榜"剧集，缺少完全失败的对照组 | 补充未上榜剧集作为负样本 |
